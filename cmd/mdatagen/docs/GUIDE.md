# Generating Component Configuration with mdatagen

This guide is for component authors who want to define a receiver, exporter, processor,
connector, or extension's configuration once — in `metadata.yaml` — and have `mdatagen`
generate the JSON Schema, the Go `Config` struct (with `mapstructure` tags, validation, and
defaults), and the configuration reference table in the component's `README.md`.

> **Status: evolving.** This capability is under active development. The schema format
> described here (the `config:`/`exported_configs:` block in `metadata.yaml`) is stable enough to use,
> but details may still change as the feature matures upstream. Treat the sample components as your reference
> implementation and expect to check [metadata-schema.yaml](../metadata-schema.yaml) for the latest
> field list before relying on anything not covered here.

## Why this exists

Every OpenTelemetry Collector component that accepts configuration used to hand-write
its `Config` struct, its `Validate()` method, its default-value constructor, and its README
configuration table separately — four places that silently drift out of sync as options are
added or renamed. The `config:` section in `metadata.yaml` gives you one source of truth.
From it, `mdatagen` generates:

- a **JSON Schema** file (`config.schema.json`) that IDEs and other tooling can use
  for autocompletion and validation,
- a **Go `Config` struct** (`generated_config.go`) with `mapstructure` tags, a `Validate()`
  method when supported validation rules are present, and a `NewDefault<Type>()`/
  `createDefaultConfig()` constructor,
- a **generated test file** (`generated_config_test.go`) exercising defaults and supported
  validation rules (see [Generated test coverage](#generated-test-coverage)),
- a **"Configuration" section** injected into the component's `README.md`.

## Quickstart

Add a `config:` block to your component's `metadata.yaml`, alongside the existing `type` and
`status` fields:

```yaml
type: myreceiver
status:
  class: receiver
  stability:
    beta: [metrics, traces]

config:
  properties:
    endpoint:
      type: string
      description: The endpoint to listen on.
      default: "localhost:4317"
    timeout:
      type: duration
      description: Request timeout duration.
      default: "30s"
  required: [endpoint]
```

Then generate as usual. If you haven't already, install `mdatagen` once:

```bash
cd cmd/mdatagen && go install .
```

and either run it directly against your component:

```bash
mdatagen metadata.yaml
```

or, if your component already has a `//go:generate mdatagen metadata.yaml` directive in its
`doc.go`, run `make generate` from the component folder to regenerate everything.

This produces (or updates) `generated_config.go`, `generated_config_test.go`, and
`config.schema.json`, plus the content between the `<!-- config autogenerated section -->…<!--
end config autogenerated section -->` markers in `README.md` — *if* those markers are already
present (see [Config docs](#config-docs) for the one-time setup if they aren't). All generated
content is marked "Code generated... DO NOT EDIT" (or bounded by autogenerated-section markers) —
edit the `config:` block in `metadata.yaml`, not the generated files.

## Anatomy of the `config:` block

The `config:` block is a JSON-Schema-flavored description of your component's configuration:

```yaml
config:
  description: string       # optional: doc string for the whole config
  $comment: string          # optional: comment for schema authors, not emitted anywhere
  type: object              # optional: object type is a default
  properties:
    <property.name>:
      description: string
      type: <see type reference below>
      default: any
      # ...validation constraints, see below
  required: [endpoint]       # optional: property names that must be set
exported_configs:
  <definition.name>:        # optional: other types exported from the component, referenced via $ref
    type: object
    properties: {}
```

Every property under `properties` becomes one field on the generated `Config` struct (or, if
it's an object, its own nested struct). `required` marks the property as mandatory in the JSON
Schema and README table. Generated `Validate()` checks required strings, slices, and maps for
nonempty values, and required pointers for nil values. It does not generate a presence check for
non-pointer numeric or boolean fields; use a suitable constraint or custom validator if those
fields need runtime validation.

## Type reference

### Primitive types

Use Go type names directly as the `type` value:

| `type` value                                  | Go type                | JSON Schema type       |
|-----------------------------------------------|------------------------|------------------------|
| `string`                                      | `string`               | `string`               |
| `bool`                                        | `bool`                 | `boolean`              |
| `int`, `int8`, `int16`, `int32`, `int64`      | matching Go int type   | `integer`              |
| `uint`, `uint8`, `uint16`, `uint32`, `uint64` | matching Go uint type  | `integer`              |
| `byte`, `rune`                                | `byte` / `rune`        | `integer`              |
| `float32`, `float64`                          | matching Go float type | `number`               |
| `any`                                         | `any`                  | *(no type constraint)* |

### Container types

| `type` value | Go type        | Requires                   | Notes                                         |
|--------------|----------------|----------------------------|-----------------------------------------------|
| `object`     | struct         | `properties:`              | Nested objects become their own named struct. |
| `slice`      | `[]T`          | `values:` (element schema) |                                               |
| `map`        | `map[string]T` | `values:` (value schema)   | Keys are always `string`.                     |

```yaml
config:
  properties:
    endpoints:
      type: slice
      values:
        type: string
      description: List of endpoints to connect to.
    headers:
      type: map
      values:
        type: string
      description: Extra HTTP headers to attach to each request.
```

### Alias types

Shorthand `type` values that expand to a primitive/container type plus Go-specific
annotations (custom Go type, format, or regex pattern) that plain JSON Schema can't express:

| Alias           | Go type                | Representation                                                      | Notes                     |
|-----------------|------------------------|---------------------------------------------------------------------|---------------------------|
| `float`         | `float32`              | `number`                                                            | Shorthand for `float32`.  |
| `double`        | `float64`              | `number`                                                            | Shorthand for `float64`.  |
| `duration`      | `time.Duration`        | `string`, pattern `^([0-9]+(\.[0-9]+)?(ns\|us\|µs\|ms\|s\|m\|h))+$` | e.g. `"30s"`, `"1h30m"`.  |
| `time`          | `time.Time`            | `string`, `format: date-time`                                       | RFC 3339.                 |
| `opaque_string` | `configopaque.String`  | `string`                                                            | Masked in logs.           |
| `component_id`  | `component.ID`         | `string`                                                            | A collector component ID. |
| `opaque_map`    | `configopaque.MapList` | `object` (`map[string]string`)                                      | Values masked in logs.    |

```yaml
config:
  type: object
  properties:
    max_results:
      type: int64
      default: 100
    timeout:
      type: duration
      default: 30s
    api_token:
      type: opaque_string
```

Alias expansion only fills in fields you haven't already set explicitly.

## Naming fields

Every property name under `properties:` becomes a Go struct field name using the same
identifier rules `mdatagen` uses elsewhere: the snake_case (or kebab-case) name is title-cased
segment by segment, and known acronyms are normalized to their canonical casing — `api_token`
becomes `APIToken`, `component_id` becomes `ComponentID`, and so on.

Override the derived name with `go_struct.field_name` when the automatic conversion isn't what
you want:

```yaml
properties:
  endpoint_url:
    type: string
    go_struct:
      field_name: EndpointURL
```

`go_struct.field_name` only changes the Go identifier. The `mapstructure` tag always keeps the
original property name from `properties:` — `mapstructure:"endpoint_url,omitempty"` in the
example above — so the config key users write is unaffected by the override.

Fields that are neither required nor have a `default` automatically get a `,omitempty`
`mapstructure` tag, since there's nothing meaningful to fall back to.

## Validation constraints

Add these alongside `type` on any property to have them enforced both in the JSON Schema and
in the generated `Validate()` method:

- strings: `minLength`, `maxLength`, `pattern`, `enum`
- numbers: `minimum`, `maximum`, `exclusiveMinimum`, `exclusiveMaximum`

```yaml
config:
  type: object
  properties:
    port:
      type: int
      description: Port to listen on.
      minimum: 1
      maximum: 65535
```

`required: [<name>, ...]` at the object level makes a property mandatory; leaving a
non-required field with no `default` makes it an ordinary zero-valued Go field (see
[Optional fields](#optional-fields) and [Pointer fields](#pointer-fields) below for `omitempty`
and pointer behavior).

`minItems`, `maxItems`, `uniqueItems`, `minProperties`, `maxProperties`, and `multipleOf` are
also accepted and flow into `config.schema.json` (so IDEs and other JSON-Schema-aware tooling
enforce them), but mdatagen does not yet generate a corresponding check in the Go `Validate()`
method — only the constraints listed above do.

## References and reuse (`$ref`, `exported_configs`)

Instead of inlining a schema, point at another one with `$ref`. Three flavors:

- **Internal** — a name defined in this file's own `exported_configs:` map: `$ref: my_def_name`
- **External** — a fully-qualified Go package path plus type name, snake_cased:
  `$ref: go.opentelemetry.io/collector/config/configtls.server_config`
- **Relative** — a local metadata definition, resolved against the component's own package:
  - `$ref: /config/configauth.config` (relative to repository root) or
  - `$ref: ./internal/metadata.metrics_builder_config` (same directory tree) or
  - `$ref: ../samplepkg.sample_config` (a sibling package's `exported_configs`)

External refs are how you pull in existing, hand-written collector config types —
`configtls.ClientConfig`/`ServerConfig`, `configretry.BackOffConfig`, `confighttp.ClientConfig`,
and so on — without redefining them:

```yaml
config:
  type: object
  properties:
    tls:
      $ref: go.opentelemetry.io/collector/config/configtls.server_config
```

Define reusable, component-local schemas under `exported_configs` in the same `metadata.yaml`, then
reference them by name:

```yaml
config:
  type: object
  properties:
    primary:
      $ref: endpoint_config
    secondary:
      $ref: endpoint_config
exported_configs:
  endpoint_config:
    type: object
    properties:
      url:
        type: string
    required: [url]
```

Other components can reuse *your* schemas too, if you export them. A `pkg`-class component
(`status.class: pkg`) can declare `exported_configs` instead of `config`, and other components
reference them with a `$ref`. From `samplepkg/metadata.yaml`:

```yaml
type: samplepkg
status:
  class: pkg

exported_configs:
  port_number:
    type: int
    description: A port number to connect to.
    minimum: 1
    maximum: 65535
  sample_config:
    type: object
    properties:
      host_name:
        type: string
        default: "localhost"
        minLength: 1
      port:
        $ref: port_number
        default: 8080
        maximum: 10000
    required: [host_name]
```

`samplereceiver/metadata.yaml` consumes it with `$ref: ../samplepkg.sample_config`, which
generates a field of type `samplepkg.SampleConfig` and imports `samplepkg`. Note that a `$ref`
can add its own constraints on top of the referenced schema — in the example above,
`sample_config.port` re-references `port_number` but tightens `maximum` from 65535 to 10000.

## Embedded fields

`embed: true` is a property-level flag you set alongside `$ref` (it only makes sense on a `$ref`
to an `object` schema). It tells `mdatagen` to splice the referenced type's fields directly into
the parent's configuration namespace instead of nesting them under the property name — the Go
equivalent of a `mapstructure:",squash"` tag, and the JSON Schema equivalent of composing the
referenced schema into the parent's `allOf` instead of listing it as one more entry under
`properties`.

Compare an embedded reference to the same reference without `embed`:

```yaml
config:
  properties:
    tls:
      $ref: go.opentelemetry.io/collector/config/configtls.client_config
      # no embed: tls settings must be set under a `tls:` key in config.
    http:
      $ref: go.opentelemetry.io/collector/config/confighttp.client_config
      embed: true
      # embedded: http settings live at the top level of this component's config,
      # alongside its other properties, with no `http:` key.
```

By default, `embed: true` still gives the field its own Go identifier (derived from the property
name, or overridden with `go_struct.field_name`) — it only changes the `mapstructure` tag:

```go
HTTP confighttp.ClientConfig `mapstructure:",squash"`
```

Add `go_struct.anonymous: true` (see [anonymous: true](#anonymous-true) below) if you also want
Go's own anonymous-embedding syntax, with no field name at all — this is what `samplereceiver`
does for its metrics builder config.

Embedding only affects code generation and documentation, not validation wiring — you never need
to call the embedded type's `Validate()` yourself. The collector's `confmap.Validate` walks every
exported struct field by reflection, regardless of its `mapstructure` tag, and calls `Validate()`
on any field that implements it, so an embedded field with its own generated `Validate()` is
already covered when the collector loads the component's config. This is also why `mdatagen`'s own
validator-collection logic skips embedded fields when building the parent's `Validate()` — calling
it there too would be redundant.

In the generated README table, an embedded field's properties are flattened straight into the
parent's table — no extra row, no sub-section of their own. That's how `metrics` and
`resource_attributes` end up as direct rows in `samplereceiver`'s top-level `## Configuration`
table even though they come from an embedded `metrics_builder_config`. A plain `$ref` without
`embed`, by contrast, gets its own row and its own nested `### <a id="...">` sub-section — see
[Config docs](#config-docs) below.

## Controlling the generated Go code

A few extension fields, all optional, shape what the generated struct actually looks like.

### Optional fields

In order to wrap the field in `configoptional.Optional[T]` it has to be annotated with
`optional: true` in the `metadata.yaml`.

If the field has a default value, the constructor uses `configoptional.Some(...)` by default.
Set `go_struct.optional_mode: default` to use `configoptional.Default(...)` for an object field.
This mode does not support primitive fields or fields with `pointer: true`.

If a field has no default value, the constructor fills it with `configoptional.None[...]()`.

Example:

```yaml
config:
  type: object
  properties:
    mode_some:
      type: string
      optional: true
      default: "foo"
    endpoint:
      $ref: /config/confignet.addr_config
      optional: true
      default:
        transport: ip4
      go_struct:
        optional_mode: default
    mode_none:
      type: string
      optional: true
```

The relevant generated Go code is:

```go
type Config struct {
    Endpoint configoptional.Optional[confignet.AddrConfig] `mapstructure:"endpoint"`
    ModeNone configoptional.Optional[string] `mapstructure:"mode_none,omitempty"`
    ModeSome configoptional.Optional[string] `mapstructure:"mode_some"`
}

func createDefaultConfig() component.Config {
    endpoint := confignet.NewDefaultAddrConfig()
    endpoint.Transport = "ip4"
    return &Config{
        Endpoint: configoptional.Default(endpoint),
        ModeNone: configoptional.None[string](),
        ModeSome: configoptional.Some("foo"),
    }
}
```

### Pointer fields

Using `pointer: true` annotation makes the field a Go pointer (`*T`); a `default` renders as `&value`.

Example:
```yaml
  # metadata.yaml
  properties:
    pointer_field:
      $ref: /pkg/module.type
      pointer: true
```
```go
  // generated_config.go
  type Config struct {
      PointerField *module.Type `mapstructure:"pointer_field,omitempty"`
  }
```

### Other `go_struct` options

#### anonymous: true

Render the field as a true Go embedded field (`` metadata.MetricsBuilderConfig `mapstructure:",squash"` ``)
with no field name, instead of `FieldName MetricsBuilderConfig`. Valid only for embedded
fields (`embed: true`). This is exactly how `samplereceiver` embeds the metrics builder config generated
from its own `metrics`/`resource_attributes` sections:

```yaml
# metadata.yaml
properties:
  my_field:
    $ref: ./internal/metadata.metrics_builder_config
    embed: true
    go_struct:
      anonymous: true
      ignore_default: true
```
```go
// generated_config.go
type Config struct {
    metadata.MetricsBuilderConfig `mapstructure:",squash"`
    APIToken configopaque.String `mapstructure:"api_token,omitempty"`
    Endpoint string `mapstructure:"endpoint"`
    // ...
}
```

#### ignore_default: true

Skip generating a default-value expression for this field (useful when the referenced type provides
its own `NewDefaultX()` that you call separately).

#### private_fields: true

Adds a placeholder embedded field, `private<Type>Fields`, to the generated struct — a hook for
fields you want on the Go `Config` (or on a nested generated struct) that have no business being
part of the YAML-driven schema: unexported, runtime-only state that user configuration never sets
directly, such as caches or derived values a component wants to carry on its own config object.

`mdatagen` only emits the placeholder; you hand-write the actual `private<Type>Fields` struct type
yourself, in a regular, non-generated file in the same package. The name follows the usual casing
rules — `Config` with `private_fields: true` gets `privateConfigFields`; an `exported_configs`
entry named `sample_config` gets `privateSampleConfigFields`.

Example, following `samplescraper`:

```yaml
# metadata.yaml
config:
  type: object
  properties:
    job_name:
      type: string
  go_struct:
    private_fields: true
```

```go
// generated_config.go
type Config struct {
    JobName string `mapstructure:"job_name,omitempty"`
    // placeholder for the private fields
    privateConfigFields
}
```

```go
// config_custom.go — hand-written, not generated
package samplescraper

type privateConfigFields struct {
    warnings []string //nolint:unused
}
```

Because this placeholder field is embedded with no `mapstructure` tag, it (and anything you put
on the hand-written type) is invisible to config decoding and marshaling — it exists purely for
the component's own Go code to read and write.

#### custom_validator

Hooks a hand-written validation function into the generated `Validate()` method, for rules that
don't fit the declarative `minimum`/`pattern`/`enum` constraints described above — cross-field
checks, parsing a string into something else, or anything else that needs real code.

Add `go_struct.custom_validator` to a property (or to the object itself, for whole-struct
validation) and `mdatagen` adds a call to a validator function named after the field, prefixed
with `validate`. Override the generated name with `go_struct.custom_validator.name` if you need
something else:

```yaml
properties:
  job_name:
    type: string
    go_struct:
      custom_validator:         # calls validateJobName(c.JobName)
  component:
    type: component_id
    go_struct:
      field_name: ComponentID
      custom_validator:
        name: checkComponentID   # calls checkComponentID(c.ComponentID) instead
```

You implement the function yourself, in a regular (non-generated) file in the same package:

```go
// config_custom.go
func validateJobName(v string) error {
    if v == "" {
        return errors.New("job_name must not be empty")
    }
    return nil
}

func checkComponentID(v component.ID) error {
    return nil
}
```

The function receives the field's own value (its Go type, by value) and returns an `error`; `nil`
means valid. Setting `custom_validator` on the object itself — the root `go_struct`, or a nested
object's — passes the whole struct (as `*T`) instead of a single field. Errors from every rule,
declarative and custom alike, are combined with `errors.Join`, so a failing custom validator never
suppresses the other validation errors.

Always set `go_struct.custom_validator.name` for an object-level validator. The "named after the
field" fallback only has a field name to work with when `custom_validator` is attached to a
property; at the object level there is no property name to derive from, so the generated function
name collapses to the unhelpful, literal `validate` — and two unnamed object-level validators in
the same package (say, one on `config:` and one on an `exported_configs` entry) would collide.

## Metrics and resource-attribute config are wired in automatically

If your `metadata.yaml` also has `metrics`, `events`, or `resource_attributes` sections (the
metrics-builder side of mdatagen), you don't need to hand-write a schema for them —
mdatagen renders an on-the-fly schema for `metrics_builder_config` from those sections and
merges it in before generating your `config:` output. That's why `samplereceiver`'s config
block can simply `$ref` and `embed` `./internal/metadata.metrics_builder_config` — the
`Config` struct ends up with the full generated `MetricsConfig`/`ResourceAttributesConfig`
squashed in alongside your own hand-declared fields, and the README table gets `metrics` and
`resource_attributes` sub-sections for free.

## Generated test coverage

For a component with a `config:` block, `generated_config_test.go` includes
`TestCreateDefaultConfig`, asserting `createDefaultConfig()` returns a non-nil config. When
`Config` has validators, it also includes `TestConfigValidate_DefaultValid` and generated
failure cases for required fields, numeric bounds, and enum values. The generator does not add
failure cases for `minLength`, `maxLength`, `pattern`, or custom validators; add tests for those
rules yourself. A package with only `exported_configs` has no `TestCreateDefaultConfig`.

Generated tests also cover supported rules on exported and nested types. If an object definition
has validators but no default, mdatagen emits a failing test asking you to add one. If there are
no supported validation rules, the file contains a comment instead of validation tests.

## Config docs

The "Configuration" table in your component's `README.md` is generated the same way as the Go
code: from the `config:`/`exported_configs:` schema.

Unlike the Go struct and JSON Schema outputs, this step only *replaces* content between two
markers — it never creates `README.md`, and it never adds the markers for you. Before the table
shows up, add both marker lines to your `README.md` once, with nothing (or a placeholder) between
them:

```md
<!-- config autogenerated section -->
<!-- end config autogenerated section -->
```

If `README.md` doesn't exist, or exists but is missing this marker pair, `mdatagen` silently skips
this step — no error, no table. This is one of the most common reasons the "Configuration" section
doesn't show up after migrating a component: the Go struct and schema generate fine, but nothing
gets written to the README because the markers were never added.

Once the markers are in place, the generated table, for every run of `mdatagen metadata.yaml` (or
`make generate`):

- lists every YAML-visible property — `properties:` entries, plus anything flattened in from
  `embed: true` fields (see [Embedded fields](#embedded-fields)) — with its type, default,
  required/optional status, and description;
- recurses into nested `object` properties, including a plain, non-embedded `$ref`, as their own
  `### <a id="...">` sub-section linked from the parent row — this is how `samplereceiver`'s
  README ends up with `## Configuration`, `### metrics`, `### metrics.default.metric`, and so on;
- marks properties with `deprecated: true` with "(**deprecated**)" next to their description.

There's no separate flag or command for the docs step beyond the usual `mdatagen metadata.yaml` —
it runs as part of the same pass that writes `generated_config.go` and `config.schema.json`.
